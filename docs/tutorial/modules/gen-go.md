## What lives here

A single Go module containing **31 sub-packages**:

```
src/impl-go/gen/go/
├── go.mod
├── dashapi/v1/                 -- OUR service
│   ├── dashapi.pb.go           -- messages, enums
│   └── dashapi_grpc.pb.go      -- server + client interfaces
└── dash/                       -- 30 upstream packages, one per .proto
    ├── acl_group/
    ├── acl_in/
    ├── acl_out/
    ├── acl_rule/
    ├── appliance/
    ├── eni/
    ├── eni_route/
    ├── ha_scope/
    ├── ha_scope_config/
    ├── ha_scope_state/
    ├── ha_set/
    ├── ha_set_config/
    ├── ha_set_state/
    ├── meter_policy/
    ├── meter_rule/             -- contains both MeterRule and Meter
    ├── outbound_port_map/
    ├── outbound_port_map_range/
    ├── pa_validation/
    ├── qos/
    ├── route/
    ├── route_group/
    ├── route_rule/
    ├── route_type/
    ├── routing_appliance/

```

> **Special cases**: upstream `prefix_tag.proto` declares
> `package dash.tag;`, so its Go package is `dash/tag`, not `dash/prefix_tag`.
> Upstream `meter.proto` declares `package dash.meter_rule;` (shares the Go
> package with `meter_rule.proto`).

## Why a separate module?

- **Reuse**: `dash-sim`, `dash-sim-client`, `dash-redis-adapter`, and
  `dashapi-runtime` all import the same generated code without duplication.
  Each consumer declares:
  ```
  replace github.com/rashmirrout/DashCenter/src/impl-go/gen/go => ../gen/go
  ```
- **Cache hygiene**: regenerating proto stubs doesn't invalidate the build
  cache of every downstream module's tests.
- **Future polyglot**: Rust will use its own `gen-rust` mirror (planned).

## How files get here

[`scripts/codegen-go.ps1`](../../../scripts/codegen-go.ps1):

1. Cleans `src/impl-go/gen/go/`.
2. Stages output under a temp directory whose path mirrors the full Go
   import path (so `protoc`'s `paths=import` semantics work).
3. Injects a `go_package` option for every upstream proto via
   `--go_opt=Mfoo.proto=<import-path>` (upstream protos don't carry
   `go_package`).
4. Runs `protoc` once with all 31 files.
5. Copies the flattened tree back into `src/impl-go/gen/go/`.
6. Preserves the module's `go.mod`.

Re-run when:
- You edit `proto/dashapi/v1/dashapi.proto`.
- You re-vendor `sonic-dash-api` via
  [`scripts/vendor-protos.ps1`](../../../scripts/vendor-protos.ps1).

## Using the generated code

### From any module

```go
import (
    dashapi "github.com/rashmirrout/DashCenter/src/impl-go/gen/go/dashapi/v1"
    dash_vnet "github.com/rashmirrout/DashCenter/src/impl-go/gen/go/dash/vnet"
    dash_types "github.com/rashmirrout/DashCenter/src/impl-go/gen/go/dash/types"
)

v := &dash_vnet.Vnet{Vni: 1001}
obj := &dashapi.Object{
    Kind: dashapi.ObjectKind_OBJECT_KIND_VNET,
    Key:  []string{"vnet-prod"},
    Payload: &dashapi.Object_Vnet{Vnet: v},
}
```

In practice you use [`dashapi-runtime/kinds`](dashapi-runtime.md) to avoid
hand-writing the `Payload:` line.

### Client-side dial

```go
conn, _ := grpc.NewClient("localhost:50051",
    grpc.WithTransportCredentials(insecure.NewCredentials()))
client := dashapi.NewDashApiClient(conn)
```

The same `*grpc.ClientConn` works against `dash-sim` and
`dash-redis-adapter` — they implement the same interface.

## What NOT to do

- **Do not hand-edit `*.pb.go`** — they'll be wiped on the next regen.
- **Do not commit changes inside `proto/vendor/sonic-dash-api/`** — always
  go through the vendor script.
- **Do not add new files** to this module manually — every file must come
  out of `protoc`.

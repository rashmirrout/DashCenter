**"Stable"** means built and tested in CI on every commit. **"Placeholder"**
means the directory and `go.mod` exist for layout, but the binary just
prints a "scaffold" banner.

## Module dependency graph

```
                    proto/ (vendored sonic-dash-api + dashapi.proto)
                            │
                            │  protoc + scripts/codegen-go.ps1
                            ▼
                       gen/go (30+ packages)
                       /     |     \
                      /      |      \
                     /       |       \
        dashapi-runtime   dashd*   dashctl*
              │
       ┌──────┼────────────────────┐
       │      │                    │
   dash-sim   dash-sim-client   dash-redis-adapter
                                       │
                                  (redis client → APP_DB)
```

`*` = placeholder. Arrows are Go `import` edges.

Key invariant: **`dash-sim-client` does NOT import `dash-sim/internal/*`.**
The CLI is transport-only — it knows about the gRPC service and the upstream
proto types, nothing more. This is what lets it work unchanged against the
adapter and (in future) real hardware.

## Module use-cases at a glance

### `dash-sim`
- **Use for**: local development, CI fixtures, hardware-free behavioural
  testing, packet pipeline experimentation (`SimulatePacket`).
- **NOT for**: SONiC interop (it doesn't write to Redis), production traffic
  (it has no data plane).

### `dash-sim-client`
- **Use for**: every `apply / get / delete / list / subscribe / counters /
  simulate` operation against any DashApi server.
- **NOT for**: direct Redis/APP_DB manipulation (use redis-cli for that, or
  better, talk to it via the adapter).

### `dash-redis-adapter`
- **Use for**: validating that your configuration produces the **exact
  APP_DB layout** SONiC's DASH orchagent expects. Bring your own Redis or
  use the built-in `--embedded-redis` for self-contained demos.
- **NOT for**: behavioural pipeline simulation — `SimulatePacket` returns
  `Unimplemented`. Use `dash-sim` in parallel for that.

### `dashapi-runtime`
- **Use for**: shared runtime code that needs to enumerate every DASH object
  kind without duplicating the per-kind switch.
- **NOT for**: per-binary state — keep `events`, `faults`, `model` etc. in
  their respective binary modules.

### `gen/go`
- **Use for**: importing `dashapi.v1` and any `dash.<area>` upstream
  message types.
- **NOT for**: manual edits — file contents are regenerated by
  `scripts/codegen-go.ps1`.

### `dashd` / `dashctl` (placeholder)
- Currently stubs. The intended split is **dashd** = central controller
  daemon (writes desired-state to many DPUs), **dashctl** = operator CLI
  for that controller (one level above `dash-sim-client`).
- Today, use `dash-sim-client` to talk to individual DPU agents (sim or
  adapter) directly. The `dashd` layer above is the next milestone after
  Phase 3.

## Module status & roadmap

| Phase | Scope | Modules |
|---|---|---|
| **Phase 1 — schema parity** | All 29 upstream DASH object kinds exposed via `DashApi`. ✅ done. | `proto/dashapi`, `gen/go`, `dashapi-runtime`, `dash-sim`, `dash-sim-client` |
| **Phase 2 — behavioural pipeline** | Full DASH packet pipeline (direction → ACL 1..5 → route LPM → vnet_mapping encap), exposed as `SimulatePacket`. ✅ done. | `dash-sim/internal/sim/pipeline` |
| **Phase 3 — SONiC adapter** | Same wire contract over Redis APP_DB matching SONiC orchagent layout. ✅ done. | `dash-redis-adapter` |
| **Phase 4 — controller** | `dashd` fleet controller, `dashctl` CLI, multi-DPU state reconciliation. ⏳ planned. | `dashd`, `dashctl` |
| **Phase 5 — Rust parity** | Mirror Phase 1 binaries in Rust. ⏳ planned. | `src/impl-rust/*` |

## Adding a new module

Checklist when introducing a new Go module under `src/impl-go/`:

1. Create the directory with `cmd/<binary>/main.go` and any `internal/` packages.
2. `go mod init github.com/rashmirrout/DashCenter/src/impl-go/<name>`.
3. Add `replace` directives for `gen/go` and `dashapi-runtime`:
   ```
   replace github.com/rashmirrout/DashCenter/src/impl-go/gen/go => ../gen/go
   replace github.com/rashmirrout/DashCenter/src/impl-go/dashapi-runtime => ../dashapi-runtime
   ```
4. Add the path to [`src/impl-go/go.work`](../../src/impl-go/go.work).
5. `go build ./...` and `go test ./...` inside the new module.
6. Add a `Dockerfile` if you want a container.
7. Add a one-pager under `docs/tutorial/modules/<name>.md` and link it from
   the table above.
